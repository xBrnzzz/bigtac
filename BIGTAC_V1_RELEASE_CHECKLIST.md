## Backend reality

Implemented: configured Firebase web SDK/Auth, frontend Firestore listeners and transactions, client role/stale-state checks, and an isolated staff-order Rules example plus emulator harness. Test servers substitute in-memory Firebase modules before execution (`tests/fixtures/server.mjs:15`, `tests/fixtures/admin-server.mjs:24`). These are useful application tests, not production authorization evidence.

Missing in this repository: trusted order creation/pricing, privileged staff service, complete deployable authorization/privacy policy and secure customer tracking contract. Redacted self-claim feed, discount engine activation, new modifier quantity/allowance pricing and new snapshot contracts are proposals or disabled models. Messaging imports alone are not a background notification service. There is no payment ledger or verified accounting. No external service's absence or insecurity is asserted without its deployment inventory.

## Remaining work, in dependency order

### P0 — before accepting real customer orders

- [ ] **P0.1 Establish the actual target and approved backend contract.** Identify live/staging URLs and deployed revisions; obtain active Rules/indexes, Auth UID memberships, service/upload configuration and catalog/settings inventory through authorized access. Back up and verify restore. Use one isolated restaurant Firebase environment for v1; no shared multi-tenant system. Approve the bounded security/order/privacy changes before implementation. Acceptance: reproducible inventory and rollback, canonical active owner account, no guessed deployment state.
- [ ] **P0.2 Implement trusted checkout.** Depends on P0.1. Submit product/offer identifiers, selected modifier identifiers (an explicit legacy adapter where needed), quantities, fulfillment details and a retry/idempotency key. The trusted service reloads authoritative catalog/configuration, validates publication/availability, selections, quantities, schedules/server time and allowed mode/zone, computes exact totals/fees, and writes validated snapshots. Preserve legacy line-total receipt compatibility. Deny browser bypass of order creation. Acceptance: tampered/stale/sold-out carts, closed modes, changed fees/options, invalid values and repeated/ambiguous retries cannot create incorrect or duplicate orders. Do not activate new discount/quantity pricing.
- [ ] **P0.3 Enforce complete authorization and private reads.** Depends on P0.1 and the P0.2 contract; can be developed alongside it. Protect membership/roles and catalog/settings writes; enforce active roles, valid status transitions, assignment and driver ownership on the backend. Define customer-specific secure tracking access and separate safe tracking/staff/fulfillment data as required, including delivery details currently placed in notes. Verify that public catalog queries expose only intended data and remain compatible with the policy. Deny cross-customer, unassigned-driver and unauthorized-role reads/writes through direct SDK/REST calls. The Phase 2 example cannot be deployed as the full policy. A self-claim feed is unnecessary while managers assign deliveries.
- [ ] **P0.4 Complete delivery destination handling.** Depends on approved order/privacy contract. Capture and validate a delivery address separately from cooking notes; persist it in the approved fulfillment data and expose it to authorized managers/assigned driver. Keep the selected fee zone distinct. Acceptance: an order placed through the actual customer flow reaches the assigned driver with usable address/contact/Maps, disappears from the previous driver on reassignment, and completes exactly once. No manually injected fixture address counts as this acceptance.
- [ ] **P0.5 Verify the real backend and release configuration.** Depends on P0.2–P0.4. Integrate a complete policy and run real emulator tests, then staging with the actual SDK and every supported role. Verify catalog/shared-group transactions and limits, data adoption without silent backfill, required order/history/driver indexes, upload preset server restrictions, revocation, forged calls, stale/concurrent actions and offline/reconnect. Validate closure races and recovery from partial pending-order rejection. No skipped emulator check or fixture permission simulation closes this item.
- [ ] **P0.6 Complete hosted acceptance and approved release.** Depends on P0.1–P0.5 and P1.1–P1.3. Record exact frontend/backend/Rules/index revisions; exclude `CC.html` bulk uploader, fixtures, nested checkouts and development tools from the production artifact. Verify actual HTTPS desktop/mobile order → restaurant → assigned driver/handoff → customer tracking, failure/retry behavior, contacts/assets and rollback. Check physical iPhone/Android keyboards, touch, dialogs/navigation and overflow at 320–390px plus tablet/desktop. Obtain separate deployment approval; no deployment is authorized by this checklist. Perform the agreed controlled pilot before opening to real customers.
